## 3. HARD CONSTRAINTS for the architecture

1. **Hooks combined with permissionless Meteora trading.** This works **only during the DBC bonding-curve phase**. DBC revokes the hook (program_id and authority set to None) on the completing swap. DAMM v2 cannot move active-hook tokens even with a badge. DLMM can, but only with an operator-granted badge, the source is closed, and SDK meta-resolution is limited. **Permanent hooks cannot exist on any permissionless Meteora path.**
2. **Custom extensions on DBC-launched tokens.** Not possible. The extension set is fixed: Metaplex metadata (SPL), MetadataPointer + TokenMetadata (T22), plus TransferHook in hook configs. TransferFee comes only with 0.2.2 (devnet now). Extensions cannot be added after mint init.
3. **Confidential transfers.** Live on mainnet since 2026-06 (ZK ElGamal re-enabled, T22 v11.0.0). They hide amounts only. **No AMM trades confidentially.** DAMM v2 and DLMM need a badge for ConfidentialTransferMint, and DBC cannot create such mints. Validators can disable them again with a kill switch (they did so in 2025 for about 12 months).
4. **PQ signature budget.** Ceilings: 4,096 B per V1 transaction (1,232 B legacy/v0), 1.4M CU per transaction, ≤64 accounts per V1 transaction with no ALTs. The only hash syscall on mainnet suited to standards-based schemes is `sol_sha256`. No PQ syscall exists. LM-OTS N32_W4 (2,180 B, ≤~0.15M CU) fits in a single V1 transaction. In legacy transactions, only ≤~650–850 B schemes fit, and hook transfers do not fit at all.
5. **CPI depth is 5.** A launchpad CPI into DBC into T22 into the hook leaves the hook one CPI. A hook can never CPI back into Token-2022 or the initiating program.
6. **Trust floor that cannot be removed when building on Meteora.** DBC, DAMM v2, DLMM, Alpha Vault, the Locker and Token-2022 are all upgradeable by Squads v3 multisigs (4-of-7 / 4-of-6) with **no on-chain timelock**. Single-key operators can disable DAMM v2 and DLMM pools and raise fees (≤10% base). The DBC and DAMM v2 licence forbids commercial forks. **Immutability can only be guaranteed for our own programs.**
7. **Launch integrity.** DBC configs are permissionless and anyone can launch on them, so only pools created by our program's PDA, or recorded in our on-chain registry, count as "ours". DAMM v2 customizable-pool and DLMM PDAs are unique per pair and can be squatted, so token custody must stay in program PDAs until the canonical pool exists.
8. **Immutability path.** Programs must be built **SBPFv3** (`--arch v3`, platform-tools ≥v1.56, v1.57 preferred) and finalized with CLI ≥4.0 (4.3.0 recommended). Do this anyway, because SIMD-0500 would block finalizing v0–v2.
9. **Build environment.** Anchor, SPL interface crates, host tests (LiteSVM/Mollusk), IDL builds and solana-verify **cannot run on this Windows machine** without MSVC or Docker. A Linux CI or remote build environment is required for the canonical build. Windows can only run Pinocchio-only SBF builds, CLI 4.3.0, Surfpool 1.6.0 and Kit clients.
10. **Toolchain compatibility.** Agave 4.3 crates need host rustc ≥1.97.1 (installed: 1.98). SBF code compiles with platform-tools rustc 1.95.0, and crates with MSRV ≤1.95 are fine (Anchor MSRV 1.89). Do not mix the Anchor solana-v3 and solana-v4 cohorts. Use `declare_program!` for Meteora, never the Meteora program crates (Anchor 1.0.2 / Solana 3.1).

**Safe config profile, enforced on-chain by the wrapper:**
- `token_update_authority=1` (Immutable); never 3 or 4.
- `migration_fee.fee_percentage=0`.
- Partner and creator unlocked LP = 0; 100% permanently locked, or vested to a fee-router PDA.
- Dynamic supply (leftover burned), or fixed supply with a keyless leftover PDA.
- Quote mint wSOL (no freeze authority).
- High-cliff exponential fee scheduler plus dynamic fee.
- `enable_first_swap_with_min_fee=false`.
- Creator allocation only via `locked_vesting`.

**Recommendation:** A, with Meteora's trust stated plainly in the UI. Optional fail-closed guard: refuse to CPI if the DBC or DAMM v2 ProgramData `last_deploy_slot` differs from the audited value. That trades liveness for safety and needs a governance path to accept new values.

### 4.2 Hooks and customization
| Option | Notes |
|---|---|
| **A. ### 4.4 Quantum resistance
| Option | Reality |
|---|---|
| "Quantum-proof token" | **Marketing only.** Holder wallets, Meteora, Token-2022 and consensus are all Ed25519/BLS based. |
| **PQ custody vault (recommended)** | Immutable program. PDA = f("pqvault", H(K0)). LM-OTS `SHA256_N32_W4` rotating key chain verified in one V1 transaction. ### 4.5 "Superintelligence-proof" (minimal-trust) security
Real and achievable for **our** layer:
- No admin keys on any path that touches funds; no pause; no privileged withdraw or migrate.
- Global config hard-coded, or initialized in the deploy transaction.
- Programs finalized (authority None) after audits and a capped rollout.
- Reproducible solana-verify builds from Linux CI, uploaded before finalizing.
- On-chain mint verifier with a default-deny extension allowlist.
- On-chain invariants checked after each state change.
- `overflow-checks`, checked math, explicit rounding.
- Assurance: LiteSVM/Mollusk tests, Trident fuzzing, Kani or Certora on curve and fee math, ≥2 audits plus a contest, a bounty, security.txt.

Residual trust that cannot be removed, and must be disclosed: Meteora multisig and operators, the Token-2022 multisig, validator feature gates, the frontend and DNS, and wallet software. If any upgrade path is kept, use Squads v4 with an on-chain time_lock of days or more, hardware keys, and no durable-nonce signing.
