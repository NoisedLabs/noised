# Noised integration tests (LiteSVM)

End-to-end tests of our on-chain programs, run in [LiteSVM](https://crates.io/crates/litesvm) 0.17 with mainnet features. We build the programs as SBPF v3. They run against the **mainnet dumps** of Token-2022, SPL Token (p-token) and the ATA program, not LiteSVM's bundled copies. The one bundled program we use is SPL Memo v2 (`MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr`), which LiteSVM 0.17 ships at its mainnet address and the vault calls before paying a memo-required account. Signatures are real LM-OTS signatures (`noised-lmots`), and vault withdrawals go out as v1 transactions, as on mainnet. The launchpad is loaded for its post-quantum launch attestation and its on-chain metadata record: `attest_launch` (PQ v2) runs the SDK's LMS vectors (`vectors/lms.json`) byte for byte, with real LMS signatures (RFC 8554 `LMS_SHA256_M32_H10`), and `publish_metadata`, `attest_launch` and `launch` run against mainnet DBC (`tests/metadata_record.rs`), so the record written from the documented layouts is what ends up in the mint. Programmable launches (PROGRAMMABLE_V1 §1.2-§3, amendments A1 and A2): the attestation message is version 3 and binds the creator's rules hash; `publish_rules`, `attest_launch` with rules and `pq_authorize` land `vectors/programmable.json` byte for byte (`tests/programmable_vectors.rs`), and the hook stores and evaluates creator rules (`tests/hook.rs`). The rest of the launchpad's lifecycle (commits, the batch, claims, fees, migration) has its own LiteSVM suite (`programs/noised-launchpad/tests/litesvm`).

This crate is **its own Cargo workspace**, with its own `Cargo.lock`, and the root workspace lists it in `exclude`. LiteSVM pins older `solana-*` crates (for example `solana-address ~2.7`). As a root member it would downgrade the programs' audited on-chain dependency graph, and it would make the root unresolvable as soon as a program needs a newer one. The `.so` files under test are built from the root workspace. The host copies of the program crates linked here only provide types and instruction builders.

## Run

PowerShell, from the repository root:

```powershell
. $env:NOISED_ENV_SCRIPT   # optional: your toolchain env script (MSVC, Agave 4.3.0, caches)
$env:CARGO_BUILD_JOBS = '4'
# Put build output on a drive with enough free space (tens of GB): set NOISED_BUILD_ROOT there.

# 1. Build the programs under test (always SBPF v3: cargo-build-sbf 4.3 defaults to v0)
$env:CARGO_TARGET_DIR = "$env:NOISED_BUILD_ROOT\target-sbf"
cargo-build-sbf --manifest-path programs/noised-vault/Cargo.toml --arch v3
cargo-build-sbf --manifest-path programs/noised-hook/Cargo.toml --arch v3
cargo-build-sbf --manifest-path programs/noised-launchpad/Cargo.toml --arch v3  # vectors_onchain, metadata_record, harness

# 2. Run every suite (add `-- --nocapture` to see the CU / size report)
$env:CARGO_TARGET_DIR = "$env:NOISED_BUILD_ROOT\target-it"
$env:NOISED_SBF_DIR = "$env:NOISED_BUILD_ROOT\target-sbf\deploy"
$env:NOISED_FIXTURES_DIR = "$PWD\fixtures"   # the default; scripts\fetch-fixtures.ps1 writes there
cargo test --manifest-path tests/integration/Cargo.toml -- --nocapture

# one suite / one test
cargo test --manifest-path tests/integration/Cargo.toml --test hook
cargo test --manifest-path tests/integration/Cargo.toml --test vault -- replay
cargo test --manifest-path tests/integration/Cargo.toml --test vectors_onchain -- --nocapture
cargo test --manifest-path tests/integration/Cargo.toml --test metadata_record -- --nocapture
```

One target dir for both steps also works (then `NOISED_SBF_DIR` is not needed). The first build of the test crate compiles LiteSVM and the Agave runtime (a few minutes, all under `CARGO_TARGET_DIR`). Dependencies are built with `opt-level = 2`, so the SBPF interpreter and the SHA-256 signing code run fast. After that, the whole suite runs in about a second (the LMS vector test generates one 1,024-leaf identity, about 1.14 million SHA-256 compressions, with `sha2` and `noised-lmots` at `opt-level = 3`).

### Where things are found

| What | Lookup order |
|---|---|
| Our `.so` files | `NOISED_SBF_DIR`, `SBF_OUT_DIR`, `<target dir of the test binary>\deploy`, `CARGO_TARGET_DIR\deploy`, `<repo>\target\deploy` |
| Mainnet dumps | `NOISED_FIXTURES_DIR`, default `<repo>\fixtures` (gitignored; `*.so`, `accounts\*.json`) |
| SDK vectors | `tests/integration/vectors/vault_withdraw.json`, `lms.json`, `metadata.json` and `programmable.json` (committed; see `tests/sdk_vectors.rs`, `tests/lms_vectors.rs`, `tests/metadata_vectors.rs`, `tests/programmable_vectors.rs`) |

A test never runs silently against the wrong binary. `paths::program_so` **fails** on a `.so` that is not SBPF v3 (ELF `e_flags != 3`). It also fails on a `.so` older than any source file compiled into it (the program plus its on-chain path dependencies). Set `NOISED_ALLOW_STALE_SBF=1` to skip the age check, and only if you know why. The age check uses file times, so it cannot see a changed root `Cargo.lock`. Rebuild after dependency changes.

## What is covered

**PQ vault v4** (`tests/vault.rs`, 39 tests). The vault PDA `["vault", mint, genesis_key_id]` never moves; every withdrawal rotates the LM-OTS key in place, reserves `min(max_amount, balance − reserved)` in a `Payout` PDA `["payout", vault, u64le(sequence)]` and moves no tokens. `release` (anyone) pays the recipient's canonical ATA, creating it if missing; `release_to` (signed by the recipient) pays any token account of the mint. The message, `key_id` and PDAs follow the documented layout byte for byte and match the program crate and `noised-lmots`. Keys follow SPEC §3.10 (`cluster | mint | u32le(account) | u32le(sequence)`; no two (cluster, mint, account, sequence) share a key). Signing the same message twice gives one signature, whose `C` is the HMAC randomizer, cross-checked against an RFC 2104 write-out and the published known answer.

- open, deposit, withdraw in a v1 transaction sent the way the SDK sends it (throwaway fee payer with 0.01 SOL, SDK config words, wire bytes per SPEC §3, 2,693 bytes, loaded data within 4 MiB, under 400,000 CU): the balance stays, `reserved`, `sequence` and the key change, the payout records vault, sequence, recipient, amount and rent payer, and nothing of the recipient's is touched. A third party then releases into the recipient's missing ATA (paying for the new account), the payout closes and its rent returns to the fee payer, whose net cost is one signature fee. The next key spends the rest with `max_amount = u64::MAX`.
- the events, decoded field by field from the documented layouts: `VaultOpened`; `VaultWithdrawn` with the amount actually reserved (not `max_amount`; 0 when nothing is left), its payout and the next key id; `PayoutReleased` with the account actually paid (the canonical ATA for `release`, the chosen account for `release_to`, the passed account for an empty payout).
- `release_to` into a non-ATA account of the recipient and into someone else's account; refused without the recipient's signature (`AccountNotSigner`), signed by another wallet (`ConstraintHasOne`), into an account of another mint, or into the vault's own token account (`ConstraintDuplicateMutableAccount`).
- `release` checks every account against the payout: another vault (`ConstraintSeeds`), another recipient or rent payer (`ConstraintHasOne`), a missing or already released payout (`AccountNotInitialized`), a destination that is not the canonical ATA (`InvalidDestination`: a non-ATA account, another wallet's ATA, the ATA under the other token program), another token account as the vault's. `withdraw` reads only the vault's ATA.
- reservations never exceed the balance, with several pending payouts released in any order; empty payouts (max 0, or nothing left) close without creating an account; a later deposit is the current key's to spend.
- rotate-only withdrawals (`max_amount = 0`) and empty payouts via `release` (destination ignored) and `release_to`.
- replay: the same instruction (`ConstraintSeeds`: the vault's sequence decides the payout address), at the next sequence (`InvalidNextKey`: the replayed message names the current key as next), two rotations later and after a late deposit (`InvalidSignature`). A message signed for another sequence fails; one signed ahead by the next key executes at its own sequence.
- rejected (`InvalidSignature`, state untouched): a flipped chain bit, a changed `C`, truncated / overlong / empty signatures, another recipient, larger or smaller `max_amount`, another next key, another key's signature, and k0's signature over the message with any field changed (tag, op, program id, vault, mint, sequence, recipient, amount, next key id). The genuine signature still executes afterwards. A next key whose id does not match (`KeyIdMismatch`) or equals the current key (`InvalidNextKey`) is refused.
- a twin vault (same genesis key, other mint) does not accept vault A's signature; a genesis key opens one vault per mint once (also after rotation); a key id that does not commit to the key is refused. A user's vault accounts 0 and 1 on one mint have their own addresses and key chains, and account 0's key is refused on account 1's vault.
- liveness: someone creates the vault's ATA and sends lamports to the vault PDA and the next payout PDAs first; open, withdraw and release still work (both token programs). Lamports sent first to the recipient's canonical ATA address (less or more than its rent) do not block `release` either: the ATA program still creates the account there, and the releaser adds only the missing rent.
- the payout rent returns to the rent payer whoever releases, also when the rent payer emptied its account (it comes back as a rent-exempt system account) or handed it to another program; deposits made after rotations land in the same account and only the current key can spend them.
- `open_vault` refuses NonTransferable, PermanentDelegate, transfer fees with a config or withdraw authority, and a close authority; it accepts a close authority of None, a fixed fee, both, and confidential transfers (withdraw + release on each).
- every key is bound to its position by its LM-OTS index (audit round 2): `open_vault` takes only `q = 0` (`q = 1`, `7`, `u32::MAX` are refused with `InvalidKeyIndex`; a key id that does not commit to the key still fails `KeyIdMismatch` first) and `withdraw` installs only `q = sequence + 1` (`InvalidKeyIndex`, checked after the signature, so a forged or replayed message still fails `InvalidSignature`, also one that names a spent key). A validly signed withdrawal that hands the vault back to a spent key (the genesis key, the previous key) or to a key of another position (ahead, `u32::MAX`, another vault account's genesis key) is refused, creates no payout and changes nothing; the key of the next position is installed. A vault moved to sequence `u32::MAX - 1` performs its last withdrawal (installing `q = u32::MAX`), then refuses every withdrawal (the wrap to `q = 0`, `q = u32::MAX - 1`, and another key of index `u32::MAX`, since no index follows it), while its last payout is still released. The program binds a key's position, not its chain: it cannot tell which vault account's chain a key of the right index comes from, so handing the vault to another chain's key is a client error that only the current key's holder could sign (the SDK and the test client derive `key(account, sequence + 1)` and refuse to sign at `u32::MAX`). The error numbers clients map are pinned by the crate's host tests: `InvalidKeyIndex` was appended as 6006 after 6000-6005.

**Launch Guard hook** (`tests/hook.rs`, 25 tests). The injected policies use the shortest timeline the launchpad writes since audit round 2: a 660 s snipe shield (60 s commit window + 600 s execution window) in a one-hour guard. Signatures only the launchpad (`hook-authority`) or DBC (its pool authority) can produce come from a `Relay` registered at that program's id, which signs with the PDA's seeds; the runtime derives the PDA from the seeds and the relay's program id, as for `invoke_signed`, and every signature in the transaction is verified. Keypairs sign wherever a real signer can.

- the meta list init is permissionless and deterministic: byte-exact TLV with two entries, the PDA `["policy", mint]` and the instructions sysvar, neither signer nor writable. It is written once only, and only for mints whose hook is ours.
- `create_policy` rejects the mint authority, random signers, the unsigned launchpad PDA, a look-alike PDA, another program signing for its own `["hook-authority"]` PDA (`ConstraintSeeds`), and another program claiming the launchpad's PDA (the runtime refuses that CPI: `PrivilegeEscalation`).
- `create_policy` signed by the launchpad's `hook-authority` PDA (a CPI from the launchpad's program id): the hook's own bounds are enforced (guard over 72 h, shield over 1 h or longer than the guard, max-wallet under 0.1% and max-buy under 0.01% of supply), the pool must be DBC-owned and match the params, the mint must use this hook, a pre-funded policy PDA does not block it, and the stored policy is byte for byte what the injected policies stand for. It is written once. It then guards DBC's real base-vault PDA (`["token_vault", mint, pool]`, owned by DBC's pool authority, the PDA `["pool_authority"]` of DBC): buys signed by that authority from DBC's program id are refused during the shield and over max-buy, then pass.
- `end_snipe_shield` (audit round 2: the launchpad's `execute_batch` ends the shield as soon as the batch has bought). Only the launchpad's `hook-authority` PDA can sign it: the fee payer and a stranger (`ConstraintSeeds`), the unsigned PDA and a look-alike (`AccountNotSigner`), another program's `["hook-authority"]` PDA and another launchpad PDA (`ConstraintSeeds`) are refused, and another program cannot sign for the launchpad's PDA (`PrivilegeEscalation`, the hook never runs).
- with the launchpad's signature it takes only a policy PDA of the hook, writable, and the real instructions sysvar: the meta list (`AccountDiscriminatorMismatch`), a copy of the policy owned by another program (`AccountOwnedByWrongProgram`), a hook-owned copy off its PDA and a stored bump that does not derive the PDA (`ConstraintSeeds`), the policy read-only (`ConstraintMut`), another account as the sysvar (`ConstraintAddress`) and no sysvar (`AccountNotEnoughKeys`) are refused.
- defense in depth, `NotInBatch`: even signed by the launchpad's PDA it runs only while the current top-level instruction is the launchpad's `execute_batch`; from the launchpad's `launch` or `commit`, from another program's top-level look-alike that reaches the launchpad through a CPI, and next to a top-level `execute_batch` it is refused. Every refusal leaves the policy byte for byte as it was, and the shield holds.
- it only moves the end earlier: called 10 s after the commit window, the shield ends at that second, only the 8 bytes of `snipe_shield_end_ts` change, and `SnipeShieldEnded {mint, pool, scheduled_end_ts, snipe_shield_end_ts}` reports the scheduled and the new end. Later calls (also after the scheduled end and after the guard) and calls at or after the scheduled end change nothing and report an unchanged end; one in the shield's last second moves the end by that second.
- buys pass right after it: in one transaction, the batch buy inside `execute_batch`, `end_snipe_shield`, then a public buy all pass, while a public buy placed before `end_snipe_shield` is refused with its whole transaction. Not mutated, because the change would be unobservable (equivalent mutants): `has_one = vault` on payouts and `has_one = mint` on vaults (the PDA seeds already bind them), the token-program owner and mint checks in `ensure_canonical_ata` after the address check (only the ATA program can put data at that address, for that token program and mint), and the memo program's address constraint (the CPI cannot run without the real program account). In the hook's `execute`: dropping `is_buy` or `now < snipe_shield_end_ts` from the `in_batch` computation, and dropping `amount == 0` from the early return for transfers that are not buys. These only change when the instructions sysvar or the token accounts are read (compute units), because the rules use `in_batch` only for buys before the shield ends and pass zero-amount transfers that are not buys anyway. In `attest_launch`: the comparison of an identity account's stored key with the presented one (`identity.public_key == lms_pk`), because the account is named by that key's SHA-256: only a hash collision could present another key. A replacement that keeps the old version, launch or identity (audit 3), because a replacement attests the same launch for the identity the launch names, so it writes the same values. In `launch_window_is_valid`: counting the minute from `now` alone (`now + 60 <= not_after` for `max(now, not_before) + 60 <= not_after`), because the same expression requires a window of at least 60 seconds, so `not_before + 60 <= not_after` always holds. In `launch`: the comparisons of the mint's TokenMetadata with the record (`checks::verify_token_metadata`, `MetadataMismatch`), because the real DBC writes exactly the strings `launch` sends; the launchpad crate's host tests compare the TLV bytes, and here the mint is compared with independently computed values, which kills every mutant that changes what is sent (L65-L70).

Several record mutants (L52-L58, L61-L63) are caught only with accounts placed by `set_account`: on a cluster only `publish_metadata` writes a `TokenMeta`, whole and at its canonical address, so the owner check alone already rules out a wrong discriminator, version, launch, hash or bump. They pin those defense-in-depth checks. L66 and L67 are caught only by the multi-byte inline document (`metadata.json`'s last case): the typical document's base64 holds neither `+` nor `/` and needs one `=`.

H23 and H24 (a transfer from the base vault into itself) are caught only by calling `execute` directly. Token-2022 returns from a self-transfer before it moves funds or calls the hook, so through Token-2022 that branch of the hook is unreachable.

## Extending (DBC / DAMM v2 end-to-end)

```rust
let mut h = Harness::builder()
    .program(LAUNCHPAD_PROGRAM_ID, "noised_launchpad")         // our .so (freshness + v3 checked)
    .fixture_program(DBC_PROGRAM_ID, "dbc.so")                   // mainnet dumps
    .fixture_program(DAMM_V2_PROGRAM_ID, "damm_v2.so")
    .fixture_account("accounts/So11111111111111111111111111111111111111112.json")
    .fixture_account("accounts/7F6dnUcRuyM2TwR8myT1dYypFXpPSxqwKNSFNkxyNESd.json")
    .build();
```

- Extend `tests/common/launchpad.rs` (today: the post-quantum attestation) and add a `tests/launch.rs` suite. Each suite binary declares `mod common;`.
- Use `expect_error(SomeError::Variant, "...")` for Anchor errors. Every one of our programs numbers its errors from 6000, so the logged name is what tells them apart through CPIs.
- Big transactions (DBC swaps with hook accounts) can use `create_lookup_table` with `send_v0`, or `send_v1` (up to 4,096 bytes, no lookup tables, at most 64 accounts). `submit` refuses any transaction over its format's size limit, because LiteSVM does not enforce it.
- `submit` gives every transaction a fresh blockhash, so re-sending identical instructions tests the program's replay protection, not the runtime's signature dedup.
- v1 transactions need both limits in their config words (unset means 0): use `v1_tx_with(fee_payer, ixs, signers, config)` with real limits, and check `loaded_accounts_data_size(&tx)` against the loaded-data limit, because LiteSVM meters less than mainnet (no programdata).
- Prefer driving PDAs through the real program (the launchpad signs for its own PDAs). To stand in for a PDA signer of a program that is not under test, register a `Relay` at that program's id and sign with `relay_signed_ix` (the runtime derives the PDA from the seeds and the relay's id, as for `invoke_signed`, and every signature stays verified), and say so in the test. `send_with_unverified_signers` (signature verification off for one transaction) is the last resort, for a signer a relay cannot produce.

## Limits of these tests

- In `programmable_vectors`, the launch and its record are placed with `set_account`, and so are the rules records `attest_launch` refuses (only `publish_rules` writes a `LaunchRules`, whole and at its canonical address, so those pin defense-in-depth checks, as for the metadata record). The launch with rules, rules on real DBC buys and the autopilot acting on authorizations are the launchpad and autopilot suites'.
- In `vectors_onchain` and in the `publish_metadata` / `attest_launch` tests of `metadata_record`, the launch is placed with `set_account` (the vectors' `Launch` v2 bytes); its `params_hash` is a fixed label hash, not the hash of real `LaunchParams`, since neither instruction reads more than its creator, `params_hash`, `pq_identity` and status. The `launch` and audit-3 tests run the real `create_launch`, but its `Protocol` account is placed (`initialize_protocol` needs the upgrade authority's programdata; `create_launch` only reads the treasury and fee share). Payout vaults, commits, the batch, pre-funded identity and attestation addresses and the rest of the lifecycle belong to the launchpad suite.
- LiteSVM has no per-account block cost tracker, so the audit-3 (F1) tests do not reproduce the write-lock contention that keeps every `launch` out of a window on a cluster: they send no `launch` inside it. What they pin is the outcome, which is the same however the window passed (contention, congestion, a keeper outage).
- Some refused records exist only through `set_account`: only `publish_metadata` ever writes a `TokenMeta`, whole and at its canonical address, so once the owner is checked no other discriminator, version, launch, hash or bump can occur on a cluster. Those tests pin the defense-in-depth checks of `attest_launch` and `launch` all the same. `attest_launch` accepts any stored bump that derives the record's address, as `launch` does (`bump = token_meta.bump`); a record at a non-canonical bump would need a `TokenMeta` that `publish_metadata` never writes, so no test places one.
- `MetadataMismatch` (the post-condition on the mint's TokenMetadata) cannot be reached with the real DBC, which writes the strings `launch` sends it; the launchpad crate's host tests compare the TLV bytes directly. Here the mint is compared with values computed independently of the program (the vectors' `tokenUri`, two base64 encoders), which catches a wrong uri that the post-condition, comparing with what was sent, would not.
- Most policies here are injected. One test runs `create_policy` itself, and the `end_snipe_shield` tests call the hook, as a CPI from a `Relay` at the launchpad's program id signed with the `hook-authority` seeds: the signature is the runtime's, the launchpad's code is not run. The launchpad's real `invoke_signed` CPIs are the launchpad suite's to exercise: `create_policy` in `launch` runs in `metadata_record`'s launches (the hook writes the policy `launch` re-reads), but no transfer is made under it there, and `end_snipe_shield` runs in `execute_batch` after the DBC swap and its checks, for its own launch's policy. The hook does not check which policy the launchpad passes; the launchpad's account constraints do.
- In the injected-policy tests the pool's base vault is an ATA of a stand-in keypair (the hook only compares account keys with `policy.base_vault`). The `create_policy` test uses DBC's real base-vault PDA and pool authority, with the account placed by `set_account` and the authority's signature made by a `Relay` at DBC's program id.
- The batch-buy tests move tokens from inside `Relay`, a native stand-in at the launchpad's program id: the hook only reads the top-level instruction's program id and data, so this is the hook's whole decision. In one transaction the batch buy and `end_snipe_shield` are two relay instructions with `execute_batch`'s tag, where the real `execute_batch` is one instruction. The real `execute_batch` (DBC swap, commits, claims, the curve-completing swap that revokes the hook) belongs to the launchpad suite; here the revocation is placed by rewriting the mint.
- The zero-amount buy tests send what the hook sees of a DBC buy whose output rounds to zero: a zero-amount `transfer_checked` out of the base vault. The DBC swap itself (a dust-liquidity first curve segment, the volatility fee it moves, `execute_batch` refusing a pool that has traded) belongs to the launchpad suite.
- A transfer from the base vault into itself is tested by calling the hook's `execute` directly. Token-2022 never calls the hook for a self-transfer, so through Token-2022 that rule cannot trigger; DBC's own refusal of such a buy is the launchpad suite's to pin.
- Hook timing is tested against the policy's stored timestamps. Validating the launchpad's own bounds belongs to the launchpad suite.
- Some vault tests sign several messages with one test key to reach individual checks. Real clients must never do this (SPEC §3). `PqKey::sign` is deterministic per message (`noised-lmots`' HMAC randomizer), so re-signing the same withdrawal reproduces its signature; `sign_with_randomizer` exists for fixed vectors. All keys are localnet keys (cluster byte 2) except in the derivation vectors.
- The confidential-transfer test configures the recipient's account with a real pubkey-validity proof, verified by the ZK ElGamal proof program; its ElGamal keys are random per run (the outcome is not).
