# Changelog

All notable changes to `@noisedlabs/sdk` (published as `@phalanx/sdk` before the project was renamed) are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). While the version is `0.x`, a minor release may break the API; breaking changes are marked **BREAKING**.

## [Unreleased]

### Changed (BREAKING): autopilot price conditions over the observed prices (review F1)

The autopilot program now judges a node's price condition across the reference and every price observed in the window (the current and the previous 15-minute bucket, however recent, the run's own observation included): `PRICE_GTE` on the lowest of them, `PRICE_LTE` on the highest, and under `NOT` the other end. Before, it read the reference alone, which one pumped (or dumped) observation in the run's own transaction could keep stale (review F1 of the framework-free rewrite, fixed before deployment). The SDK mirrors it exactly, pinned by regenerated program vectors (`test/vectors/programmable/autopilot.json`: every earlier input unchanged, 97 earlier `plan_run` cases now `ConditionFalse`, 320 new cases of compound price conditions):

- **BREAKING:** `RunInput` (`planRun`) has a required `observed: Seen | null`: every price the window holds however recent (`observedPrices(observations, now)`; `afterObservation` now also returns it as `observed`). `seen` stays the minute-old window that bounds buybacks.
- New: `conditionPrices(reference, observed)` (the range price conditions must hold across), `graphConditionOver` / `graphRunnableOver` and the `PriceRange` type (the crate's `Graph::condition_over` / `runnable_over`), `evalConditionBounded` (three-valued evaluation), `observedPrices` (the program's `reference::observed`). `graphCondition` / `graphRunnable` (one price) are unchanged.
- `nodeCondition`, `nodeStatus`, `findDueNodes` and `simulateGraph` decide price conditions this way, so a step is due only if the program would accept it; `explainGraph` says "the price has stayed at least / at most ..." and states the rule among the guarantees.

## [0.9.0] - 2026-10-13: first public release (renamed to Noised)

The first version published to npm, as `@noisedlabs/sdk`. It contains the rename below, the audit-round-4 client fixes listed under "0.9.0 (development)" and everything from the unreleased 0.1-0.8 development versions.

The project is now **Noised** (website: noised.fun), and this package is `@noisedlabs/sdk` (it was `@phalanx/sdk`). Entries below this one keep the name of their time, except file paths: the paths they cite name today's files (`programs/noised-*`, `crates/noised-*`, `idls/noised_*.json`), which were `phalanx-*` and `phalanx_*.json` then. Nothing on-chain changes: the same program ids, instructions, accounts, events, errors and discriminators (the regenerated IDLs differ only in their names), and the same signatures and key derivations byte for byte. Every domain tag fed into a hash, HMAC, HKDF, PRF or signature keeps its original spelling (`phalanx/pq/identity/v1/seed`, `phalanx/pq/lmots/C`, `phalanx/pq/passkey/v1`, ..., and every `PHX-...` tag): changing one would change every signature and every key derived from a phrase or passkey. The test vectors are unchanged, byte for byte.

### Changed (BREAKING)

- The package is `@noisedlabs/sdk` (and `@noisedlabs/sdk/programmable`); the IDLs are `noised_launchpad.json`, `noised_hook.json`, `noised_vault.json`, `noised_shield.json` and `noised_autopilot.json` (`metadata.name` `noised_*`), exported as `@noisedlabs/sdk/idl/noised_*.json`.

### Migration: records kept under the earlier name keep binding their keys

- Every ledger (`createLeafLedger`, `createVaultKeyLedger`) copies the records it finds under `phalanx/pq/...` to their new keys before its first operation (never overwriting, never deleting), reads a record under its earlier key when the new one holds none, and claims the earlier key first when it reserves (the atomic `add` earlier clients reserve with): a leaf or vault key an earlier client used, or uses later on the same store, is never given to a second message. `migrateLegacyLedgerRecords(store, namespace)` runs or reports the copy.
- The ledger locks and the signing lock are also taken under their earlier names (`phalanx/pq/...`, outer), so a tab still running the earlier release and one running this one never sign at the same time.
- `importLeafRecords` and `importVaultKeyRecords` accept exports made before the rename (`LEGACY_LEAF_LEDGER_EXPORT_FORMAT`, `LEGACY_VAULT_KEY_LEDGER_EXPORT_FORMAT`); `lmsKeyPair` loads a tree cache kept under its earlier key (`lms.legacyTreeCacheKey`; the cache is checked by its tag either way).
- Test and script settings are `NOISED_*` (`NOISED_REGEN_VECTORS`, `NOISED_DIFF_FILE`, `NOISED_RULES_VECTORS`, ...); the `PHALANX_*` names are still read for one release.

### Fixed

- `buildSwapTx` on the bonding-curve (DBC) path failed under plain Node ("BN is not a constructor"): `@coral-xyz/anchor` exposes `BN` only on its default export when Node's ESM loader imports it, while bundlers (and so the app and the tests) expose a named export. It now uses `anchor.BN ?? anchor.default.BN`. Found by the live devnet run, which builds swaps from Node; the MCP server, keepers and the LangGraph example were affected.

### Security

- **ID-F1, an RPC could steer the identity's leaf onto one that already signed** (poc_identity_steer). The leaf a message is signed at no longer depends on what the RPC reports: the walk starts at a **secret** probe (`HMAC-SHA256(probeKey, "phalanx/pq/identity/leaf/v2" || message)`, `probeKey = HMAC-SHA256(SEED, "phalanx/pq/identity/leaf/v2/key" || I)`, client-side only), and skips only leaves the ledger or this process holds. Before anything is reserved, the signers refuse while the identity's bitmap shows used leaves this ledger never signed at, or the chosen leaf is set on-chain (`UnknownLeavesError`, with counts: "this quantum key was used elsewhere"); the user imports the other device's records, or confirms with `acknowledgeUnknownLeaves(ledger, publicKey, used, { expectedCount })`. A lying bitmap now refuses instead of steering.
- **ID-F2b / ID-F3, a forged "other device" export could re-point a message onto another leaf.** `importRecord` / `importLeafRecords`: a record without a signature is not authenticated, so it only marks its leaf taken (`burned`, no message); no import ever re-points the index of a message that holds a live record at another leaf. A signed record comes in as `signed` (its landing claims are read from the chain again).
- **ID-F4, the pending-attestation guard was check-then-act** (poc_identity_pending_race). "Is an earlier signature pending, reserve, sign" runs under the launch's signing lock in `buildAttestLaunchTx` and `buildPqAuthorizeTx` (`signingLockName(launch)` = `"phalanx/pq/sign/v1/<launch>"`; default an in-process mutex; `signingLock` takes `(name, fn) => navigator.locks.request(name, fn)` in a browser): concurrent calls sign at most one new window. A signature stays pending until its landing is seen with a known outcome (the attestation or authorization account holds it) or its window ended on both clocks: a leaf bit the RPC reports set is no longer enough (`PendingAttestation.leafSetOnChain`), and `landOrBurnPending` confirms each landing it makes.
- **ID-F2, no bound on signatures that never landed.** At most `MAX_UNLANDED_SIGNATURES` (3) signatures of one launch (attestations), or of one (launch, kind) (`pq_authorize`), that never landed with success; a fourth needs `acknowledgeExtraSignatures: true` (`SignatureCapError { launch, what, leaves, count, max }`). Retired landings (`landOrBurnPending`) and rebuilds of recorded signatures do not count.
- **ID-F6, the reviewed message was compared after signing** (poc_identity_postcheck). `buildAttestLaunchTx({ expectedMessageHash })` compares the message it built with the reviewed one before reserving a leaf; `buildPlannedAttestTx` passes `plan.messageHash`. The builders read the identity's key pair, cluster and id once.
- **ID-F1b / ID-F5, a lying RPC clock could stretch what the identity signs** (poc_identity_freeze_clock). Before any signature that names a time (an attestation window, an activation, a freeze expiry), the cluster clock must agree with this device's clock, and with a second RPC's when given, within 120 s (`checkClockSkew`, `ClockSkewError`, `CLOCK_SKEW_MAX_SECS`; options `localNowSecs`, `secondConnection`, `maxClockSkewSecs` on every builder and plan that signs a time). An attestation window must suit both clocks (within `MAX_LAUNCH_LEAD_SECS`); a freeze may be used at most 24 hours after this device's clock (`FREEZE_MAX_VALID_SECS`, in `planFreeze` and `buildPqAuthorizeTx`). Every plan and status gives its times as absolute UTC dates too (`windowIso`, `activateAtIso`, `earliestActivateAtIso`, `applyAtIso`, `notAfterIso`, `expiresAtIso`, `freezeNotAfterIso`; `unixToIso`, `unixToUtcText`).
- **C1, an autopilot payee that could never receive its share** (poc_custody_autopilot_recipient). Graph recipients are checked like fee recipients (`checkGraphRecipients`): `planGraphActivation`, `buildPublishGraphTx` and `buildPublishGraphV1Tx` refuse a PQ vault of another mint (its share would be lost for good), any other vault-program account, token accounts, mints, programs and off-curve addresses with no account; another program's account and a recipient without a wSOL account yet are cautions (`warnings`).
- **C2, spam could delay re-broadcasting a revealed withdrawal** (poc_custody_search_spam). `findPendingWithdrawal` reads a successful transaction that names the current payout PDA (it cannot have run a withdrawal at this sequence, anyone can land one for the base fee) after every failed attempt; the search still reads it before calling itself complete. Its notes and docs say so.
- **M4, keepers funded recipients' accounts** (audit4_custody_keeper). `buildRunTx` never creates a recipient's wSOL account (the program skips a recipient without one and keeps its share in the treasury); it refuses a distribution nobody can receive (`NoRecipientAccount`, 6042) and creates only the caller's own tip account. `planKeeperStep` / `runKeeper` state what each step costs and what a run should earn.
- **OBS, keepers ran buybacks on others' observations.** A keeper plans a buyback only a minute after its OWN `update_price` (`ownObservationAt`; `runKeeper` tracks it), never on observations others made.
- **Zeroization.** LM-OTS secret material (`secret()` copies, chain-walk buffers) and the key derivation's concatenated master are wiped after use. Signatures are unchanged byte for byte.

- **The `Autopilot` account is 1,244 bytes** (A4-S, A4-2): `active_auth` (1,076), `active_activate_at` (1,108) and `partial_spent: [u64; 16]` (1,116) appended; `VERSION` stays 1. `AUTOPILOT.ACCOUNT_LEN` 1,244, `AUTOPILOT.OFFSETS` (every field), `AUTOPILOT.A4_EXTRA_RENT_LAMPORTS` (1,169,280 more rent for `init_autopilot`), `QSL1.AUTOPILOT.LEN` 1,244 and its `ACTIVE_AUTH_OFFSET`, `ACTIVE_ACTIVATE_AT_OFFSET`, `PARTIAL_SPENT_OFFSET`. `AutopilotAccount` gains `activeAuth`, `activeActivateAt`, `partialSpent`, `activeAuthOrNull`; `autopilotStateOf` fills `partialSpent`.

### Changed (BREAKING)

- **QSL-1: there is no level 3** (R2; docs/standard/QSL-1.md revision 0.4). Levels are L1 No-rug and L2 Quantum-attested. "Programmable" is a description shown next to the level ("QSL-1 L2 · programmable", "read its rules"), never a safety claim, and it never raises or lowers a level. `QslLevel` is `0 | 1 | 2` (`level`, `wouldBe`); `QslCheck.level` is `1 | 2`; `QSL1_CONDITION_IDS` lists `cluster`, C1.1..C1.24 and C2.1..C2.8 only (the `C3` verdict is gone); at level 2 `blocking` and `reasons` are empty. An autopilot program that can still be upgraded (P.G5) is a warning, no longer something that holds a level back.
- **`qslBadge`**: `QslBadgeLabel` no longer has `"QSL-1 L3"` and `QSL1_LEVEL_NAMES` has keys 1 and 2 only ("Programmable" is gone). `QslBadge.programmable: QslBadgeProgrammable | null` is new (see Added); its sentence and warnings come right after the summary in `lines`. ## [0.5.0] - unreleased: the quantum security layer (QSL-1)

Phalanx is the quantum security layer for Solana: Launch (tokens nobody can rug, not even their creator), Vault (post-quantum custody), Shield (private balances) and Verify. This release adds the checker of its token standard, QSL-1 (`docs/standard/QSL-1.md`), with the badge an app may show, and the client mitigation of audit round 3 review info #2 (older attestation signatures that never landed can take a freed slot). The programs, their accounts and the transactions the builders make are unchanged.

### Added

- **QSL-1** (`src/qsl/`): `checkQsl1(conn, mint, { commitment? }) -> QslResult` runs the standard's verification algorithm (§7) on live accounts: the genesis hash (levels exist on mainnet-beta only), then the reads of §7.10 (one `getMultipleAccounts` for the mint, the certificate, the hook accounts and the programs; one for the launch, the DBC config and pool, the attestation, the identity and the record; after migration the launch authority's position NFTs, their positions and pools), at `finalized` by default and each no older than the one before (`minContextSlot`); never `getProgramAccounts`, never a URL. Every condition C1.1..C1.24 and C2.1..C2.8 is re-checked from the accounts at the standard's offsets (§5), never from the certificate's flags, and a missing, foreign, short or undecodable account fails the condition that reads it. `QslResult { standard, mint, slot, cluster, level, candidate, wouldBe, components, graduated, migrated, checks, reasons, blocking, info, trusted, uriMode }`; each check is `{ id, level, title, status: "pass" | "fail" | "warn" | "skip", ok, plain, detail }` with a plain-English `plain` sentence for a badge UI. A level is awarded only with finalized Phalanx programs (C1.24: the launchpad, and the hook while it is active) on mainnet; a mint that meets every other condition of a level is `candidate: true` (level 0, `wouldBe` the level). Level 3 (Programmable) is reported as not available yet (§6.4 is a draft). `info` holds §6.6's checks (batch caps, the batch as first trade, the graduated pool's status and fee, Meteora's and Token-2022's code, the record's uri mode, the identity's leaves used); `trusted` §8.2's parties with their live upgrade authorities.

- **Older attestation signatures (audit round 3, review info #2).** `leafLedger.launchSignatures(ledger, identityId, launch) -> LaunchSignature[]`: every (window, message hash) the identity signed for a launch, read from the signed bytes the ledger keeps. `findPendingAttestations(conn, { launch, lmsPublicKey, ledger, nowSecs? }) -> PendingAttestation[]`: the launch's signatures that were never seen landing (leaf clear on-chain) and whose window has not ended, each with `landingNow: "attests" | "burns"`. `landOrBurnPending(conn, { launch, identity, ledger, payer, burnOnly?, allowLocalnet?, ...AttestTxOptions }) -> { landings, remaining }`: re-sends those recorded signatures (never a new one) through `sendAttestLaunchTx`; with `burnOnly` only the ones that would just burn their leaf (run it while the launch's attestation holds the slot). `fundingLamportsForPending(conn, { launch, identity, ledger, count? })`. `PendingAttestationError { launch, pending }`.
- `getLaunchFlowStatus(conn, launch, { pending: { ledger, lmsPublicKey } })` lists the pending signatures (`pendingSignatures`), and every status carries `warnings`: at `window-missed`, that an older signature can still take the slot; while the attested window holds the slot, that pending signatures should be retired now.

## [0.4.0] - unreleased: on-chain metadata

Mirrors the launchpad's on-chain metadata (the final programs: `publish_metadata`, `TokenMeta`, attestation message v2, `launch` without arguments, certificate v3) and the client sides of audit round 3 (F1 replaceable expired attestations, F2 immutable-owner destinations while the Launch Guard is on, F3 fee recipients). A token's name, symbol, description, icon and links are now a record on chain, at the address of its own hash, which the creator's post-quantum identity signs; nothing is hosted anywhere, and the mint's uri is empty by default. Launches, attestations and certificates of 0.3.0 are not compatible with these programs. Migration notes for each breaking change are inline.

### Changed

- **BREAKING: the token's metadata is a record published before the attestation, not a launch argument.** The flow is `planLaunch` -> `buildPlannedCreateLaunchTx` -> `buildPlannedPublishTx` / `sendPublishMetadataTx` -> `waitForTokenMeta` (finalized) -> `buildPlannedAttestTx` -> `sendAttestLaunchTx` -> `buildSweepPayerTx` -> `buildPlannedLaunchTx`. The record is `{ name, symbol, flags?, uri?, doc? }` (`TokenMetaInput`; `LaunchMetadata` is now this type): `doc` is the document `buildMetadataDoc` writes, and `flags` is 0 (the default: the mint's uri stays empty), `METADATA.FLAG_INLINE_URI` or `METADATA.FLAG_EXTERNAL_URI`. Migration: build the document (`buildMetadataDoc({ name, symbol, description, iconPng, links })`), pass `metadata: { name, symbol, doc }` to `planLaunch`, publish it, then attest.
- **BREAKING: `LaunchParamsInput` is `LaunchParams`** (no `name`, `symbol`, `uri`): `validateLaunchParams` and `buildCreateLaunchTx` no longer take or check metadata. `validateMetadata` and `validateMetadataBytes` are removed: use `validateTokenMeta(record)`, which checks the whole record exactly as `publish_metadata` does, in its order (6045 flags, 6046 lengths, 6016 name, symbol and external uri, 6045 uri modes).
- **BREAKING: attestation message v2** (`"PHX-ATTEST-V2"`, 189 bytes: launchpad, launch, params_hash, creator, `metadata_hash`, window). `metadata_hash` is `metadataHashV2(record)` = `SHA256("PHX-META-V2" || u32le(len) name || u32le(len) symbol || u8 flags || u32le(len) uri || u32le(len) doc)` over UTF-8 bytes. `launchMetadataHash` (v1) is removed, and so are `pqIdentity.metadataBytes`, `metadataJsonSha256`, `validateAttestMetadata`, `attestMetadataIsValid`, `ATTEST_METADATA_LIMITS` and the `MetadataField` type. `AttestationMessageFields` loses `metadataJsonSha256`. `PQ_IDENTITY`: `ATTEST_MESSAGE_TAG` `"PHX-ATTEST-V2"`, `ATTEST_MESSAGE_LEN` 189, `METADATA_HASH_TAG` `"PHX-META-V2"`, `ATTESTATION_ACCOUNT_LEN` 2,676, `ATTESTATION_VERSION` 2.

Before reserving a leaf it now also refuses a record that is not published, or not FINALIZED (`metadataCommitment`, default `"finalized"`; `"confirmed"` accepts a confirmed one): a record lost in a dropped fork turns the attestation into a burn. The builders refuse a launch whose attested record does not exist (AccountNotInitialized). The legacy `launch` transaction is a constant 987 bytes for every record. `buildPlannedLaunchTx` and `buildPlannedLaunchCommitBundle` keep their signatures.

- Constants and helpers: `METADATA` (seed, limits, flags, prefixes, `MAX_INLINE_URI_LEN` 4,125, the `TokenMeta` discriminator, offsets and fixed length 91, `MINT_BASE_LEN` 386, the error codes, the publish config words, the document schema's limits), `CERTIFICATE` (version 3, 487 bytes, offsets), `POLICY.MAX_DOC_LEN`, `SEEDS.metadata`; `tokenMetaAddress(launch, hash)`, `tokenMetaPda`; `rentExemptLamports(conn, size)`, `customErrorCode(error)`.
- Program errors from the new launchpad IDL: 6045 `InvalidMetadataFlags`, 6046 `MetadataTooLong`, 6047 `MetadataMismatch` (unreachable with an honest DBC), and 6016 `InvalidMetadata` with its new message.

### Fixed

- `encodeIndexedPng` no longer leaves an unhandled promise rejection behind when the platform's `CompressionStream` fails (it rejects with that error).

### Notes

- `INLINE_URI` and `EXTERNAL_URI` are supported by every builder and checker, but do not offer `INLINE_URI` in a product until the wallet/indexer matrix of METADATA_ONCHAIN.md section 2.4 passes (the DAS indexer stores uris in a `varchar(200)`). The default empty uri shows the name and symbol everywhere, and the icon in Phalanx and any reader of the record; an external uri is the creator's own link, whose content can change.
- The Launch Guard after F2 (audit round 3 F4): during the guard it stops wallet-to-wallet token transfers and, with immutable-owner destinations, consolidation by reassigning a token account's owner. It does not stop control of a position changing with no token transfer, which no hook can see: a wallet several people control (a multisig, a smart wallet's members, a shared key); a token account owned by a PDA or a smart wallet whose own program hands control to someone else; a PQ vault whose holder signs `withdraw` with `max_amount = 0` (a pure key rotation that reserves and moves nothing) and `next_key` set to another party's LM-OTS key; and a delegate approval (`Approve`), which gives revocable, shared control and lets the delegate sell during the guard (sells always pass). The shield escrow and the recipients' associated token accounts each count against one max-wallet during the guard. Anyone may fill a PQ vault's batch quota (R3-2) by naming that vault as the token owner of its own commit: the tokens that commit buys go to the vault, but its unspent or refunded wSOL goes to the refund owner it chose itself (`commit` fixes `token_owner` and `refund_owner` separately at the first commit, and `claim` pays each its part), normally its own wallet. So the attack costs only the part of the commit the batch spent; the vault's holder then commits naming another vault or its own wallet.

## [0.3.0] - unreleased: follow-ups to PQ v2 before publishing

API consolidation and hardening on top of 0.2.0 (which was never published): the recipient is confirmed before any vault signature (and what is signed is exactly what was confirmed), no raw one-time signer is reachable from the package, the signers remember in-process every one-time key and leaf they used, one type for "now", one canonical helper each for the launch window and the metadata hash, an authenticated vault-key ledger export / import, and `@solana/web3.js` as the one peer dependency. Migration notes for each breaking change are inline.

### Changed

- **BREAKING: the recipient is confirmed BEFORE any vault signature.** `prepareWithdrawal` and `signWithdrawal` require `opts.confirm: RecipientConfirmation` (no default): `{ recipient: await checkRecipient(conn, destinationOwner, mint, vault, { wallet }), acknowledged: { recipientWarnings?, mintWarnings?, offCurveConfirmation? } }`, each acknowledgment `true` exactly where the check holds that kind of caution (`acknowledged: {}` when it holds none). They refuse with `RecipientConfirmationError` (`reason`: `missing`, `mismatch` for a check of another recipient, mint or vault, `refused`, `unacknowledged`, `stale`) before any signature exists and before the vault-key ledger is written. The check runs again right before the key is reserved: a refusal or a caution the user was not shown refuses (`stale` / `refused`, with the fresh check in `error.current`). A withdrawal the ledger already holds is still returned without the re-check (nothing new is signed). Migration: `WithdrawalRequest` loses `wallet` (pass it to `checkRecipient`) and `confirmOffCurve` (now `acknowledged.offCurveConfirmation`); `PreparedWithdrawal.recipient` is the re-run check.
- **BREAKING:** `RecipientCheck` gains `destinationOwner`, `mint`, `vault` and `wallet` (what a confirmation binds to). `checkRecipient` throws a `TypeError` for inputs that are not `PublicKey`s.
- **BREAKING: no raw one-time signer is exported.** `lmots.sign` and `lmots.signDeterministic` are internal (like the LMS leaf signers since 0.2.0): with a derived `skSeed` they signed around the vault-key ledger. The `lmots` namespace keeps `publicKey`, `publicKeyBytes`, `keyId`, `verify`, `candidatePublicKey`, `randomizer`, `hmacSha256` and the constants. A vault key signs only through `prepareWithdrawal` / `signWithdrawal`; no `exports` path reaches the internal modules (checked on the packed tarball).
- **BREAKING: one type for "now", a `bigint` of unix seconds named `nowSecs`.** `launchPhase(launch, nowSecs)` and `batchOutcome(launch, nowSecs)` take a `bigint` (were `number`), and so does `VerifyOptions.nowSecs` (was `number`). `LaunchTxOptions`, `LaunchCommitBundleOptions`, `getLaunchFlowStatus`, `planLaunch` and the window helpers already did. Why `bigint`: the programs' clock and every timestamp the SDK decodes are i64 (`LaunchAccount.commitEndTs`, an attestation's window, `clusterUnixTime`), and the SDK maps every i64 to a `bigint`, so comparisons need no conversion and cannot round, while a `number` would also admit `NaN`, fractions and silent mixed comparisons (`5 < 10n` is `true` in JavaScript). A `number` is now a `TypeError` and a value that looks like milliseconds a `RangeError`. Migration: `launchPhase(l, unixNowSecs())` (or `BigInt(Math.floor(Date.now() / 1000))`).
- **BREAKING: one canonical export each for the launch window, the clock and the metadata hash**, all at the package root (`launchWindowIsValid`, `launchWindowProblems`, `inLaunchWindow`, `validateLaunchWindow`, `defaultLaunchWindow`, `unixNowSecs`, `clusterUnixTime`, `launchMetadataHash`, `ATTEST_LANDING_MARGIN_SECS`), every time parameter named `nowSecs`:
  - `pqIdentity.launchWindowIsValid(landsAt, …)` is removed; the root `launchWindowIsValid(nowSecs, notBefore, notAfter)` is now exactly `pq::launch_window_is_valid` at any plausible `nowSecs` (it used to also refuse valid windows above 10^11 s as "milliseconds"); `launchWindowProblems` is empty exactly when it holds, reports window ends outside i64 as a problem, and adds the milliseconds hint only to an invalid window.
  - The window helpers check their `nowSecs` like every other "now": `launchWindowIsValid`, `launchWindowProblems`, `inLaunchWindow` and `validateLaunchWindow` (`opts.nowSecs`) throw a `TypeError` for a `number` and a `RangeError` for a value outside i64 or that looks like milliseconds (|nowSecs| >= 10^11), so `inLaunchWindow(BigInt(Date.now()), …)` throws instead of answering "not in the window". `notBefore` / `notAfter` must be bigints (`TypeError`, also in `launchWindowProblems`, which used to return a problem for them); `defaultLaunchWindow` throws a `TypeError` for a non-`bigint` `opensAt`.
  - `pqIdentity.defaultLaunchWindow` is removed (use the root one).
  - `pqIdentity.metadataHash` is removed: use `launchMetadataHash(name, symbol, uri)` (strings or raw bytes; anything else is now a `TypeError`).
  - `pqIdentity.validateLaunchWindow` and `pqIdentity.unixNowSecs` moved to the root, and `validateLaunchWindow`'s option `now` is `nowSecs` (passing `now` throws a `TypeError` that says so).
  - `pqIdentity.DEFAULT_LANDING_MARGIN_SECS` is removed (use `ATTEST_LANDING_MARGIN_SECS`, the same 300 s).
  - `pqIdentity` keeps the window bounds `MIN_LAUNCH_WINDOW_SECS`, `MAX_LAUNCH_WINDOW_SECS`, `MAX_LAUNCH_LEAD_SECS`.
- **BREAKING: vault-key ledger records hold their one-time key, and every recorded signature is verified under it.** `VaultKeyLedger.reserve(keyId, message, info)` and `adoptFound(…, info)` require `info.key` (it must hash to `keyId` and have `q = sequence`, and the message must name `info.vault` and `info.sequence`); `recordSignature` and `adoptFound` refuse a signature that does not verify under the key and a next key that does not hash to the message's next key id, writing nothing. `VaultKeyRecord` gains `key` (null in records written by 0.2.0, which stay readable) and the origin `imported`; the interface gains `list()` and `importRecord(record)`. Migration: an app that writes records itself (the migration of stored withdrawals) passes `key: <the signing key's LmotsPublicKey>`.
- **BREAKING (packaging): `@solana/web3.js` (`^1.98.4`) is a peer dependency**, so an app and the SDK share one copy (the API takes and returns web3.js objects and checks `PublicKey` and `Transaction` with `instanceof`). Install it in your app; the SDK keeps 1.98.4 as an exact dev dependency for its own tests. The range admits the current 1.x client stack (`@solana/wallet-adapter-base` 0.9.28 needs `^1.99.0`), so npm installs the SDK without `--legacy-peer-deps`. `@solana/spl-token` (0.4.14) and `@coral-xyz/anchor` (0.31.1) stay ordinary exact dependencies, as in 0.2.0: none of their objects crosses the API (anchor only supplies the `BN` numbers handed to Meteora's quote functions), and they resolve `@solana/web3.js` to the app's copy.
- **BREAKING:** `importVaultKeyRecords` requires the export's `skipped` list (a malformed one refuses the import, writing nothing) and its summary gains `unverifiable`: the keys the other device signed with but could not export (records of SDK 0.2.0 without their key). Nothing is written for them; never sign on this device while it is not empty (run `completeVaultKeyRecords` on the other device and import its new export).
- `prepareWithdrawal` and `signWithdrawal` work on private copies of their inputs taken at the call (the request, `mint`, the message, the key, the next key and `opts.confirm` with its keys, cautions and acknowledgments), re-run `checkRecipient` for the recipient, mint and vault of the message being signed, and match the confirmation against the exact bytes right before signing. `request.maxAmount` must be a u64 (`RangeError`, before anything is read). `signWithdrawal` wipes its copy of `key.skSeed` before returning and refuses when `key.skSeed` changes while it runs (a lock), as `prepareWithdrawal` does for `master`.
- The vault signers' in-process guard (one message per one-time key) now knows every signature the process saw, not only those it computed: one returned from the ledger, adopted from chain or found by `findPendingWithdrawal`, or carried by a `VaultKeyInUseError`. A key it knows is spent is refused before anything is written to the ledger passed.
- `leafLedger.reserveAndSign` refuses (`LeafLedgerError`) a ledger whose record is not this identity's reservation of that leaf for that message, and, in one process, never signs a second message at a leaf, whatever ledger it is given (`LeafConflictError`, before anything is written). `selectLeaf` (and `signAtNextLeaf`) skip the leaves this process signed another message at. A custom `LeafLedger` must keep the contract of `createLeafLedger`.
- `prepareWithdrawal` and `signWithdrawal` give a record of SDK 0.2.0 (no key) of the key they use its key, authenticated, so that it can be exported.
- `clusterUnixTime` throws an error naming the RPC when the Clock sysvar is not plausible unix seconds (|t| >= 10^11); `verifyLaunch` reports such a clock as the warning `rpc.clock` and judges the phase on this device's clock instead of throwing.
- `decodeIdentity` (and `fetchIdentity`) refuse an `Identity` account of another version than `PQ_IDENTITY.IDENTITY_VERSION` (1) and an LMS key whose typecodes are not 6 / 3: `attest_launch` writes nothing else.
- `sendAndConfirm` documents that `commitment` is what it waits for.

### Added

- `exportVaultKeyRecords(ledger, { vault? })` and `importVaultKeyRecords(ledger, exported)` (`VAULT_KEY_LEDGER_EXPORT_FORMAT`, `VaultKeyLedgerExport`, `VaultKeyImportSummary`, `VaultKeyImportOutcome`): several devices holding one phrase, at parity with `exportLeafRecords` / `importLeafRecords`. An import authenticates every record (its signature must verify under its recorded key over its recorded withdrawal) and writes nothing if one fails; it only adds (a key the other device signed becomes taken; a local reservation that never signed gives way) and reports `conflicts` and `compromised` keys. The multi-device rule is documented in `vaultLedger` and the README.
- `recordPendingWithdrawal(ledger, search)`: records `findPendingWithdrawal`'s `pending` withdrawal in the vault-key ledger (verified under the vault's current key), so `buildWithdrawTxWithFallback` can re-broadcast it.

- `completeVaultKeyRecords(ledger, master, cluster, mint, maxAccount) → VaultKeyCompletion { completed, remaining }`: gives the records of SDK 0.2.0 of this phrase's vault accounts their one-time key (re-derived, then authenticated by `importRecord`), so `exportVaultKeyRecords` can carry them; nothing is signed.
- `SendOptions.preflightCommitment` (default `confirmed`): the commitment of `sendAndConfirm`'s preflight and default expiry height, for transactions built with a blockhash of another commitment.
- A `NOTICE` file in the package (and `LICENSE` / `NOTICE` at the repository root), and `src/idl/LICENSE-meteora`: the MIT license text (with Meteora's copyright line) of the vendored Meteora IDLs.

### Fixed

- `sendAndConfirm(conn, tx, { commitment: "finalized" })` ran its preflight at `finalized`, where the builders' fresh `confirmed` blockhash is not known yet (BlockhashNotFound), and computed the default expiry from the lagging finalized block height. It now preflights and computes the default expiry at `preflightCommitment` (default `confirmed`), and waits at the requested commitment.
- Review round 2 of this release:
  - The recipient confirmation could be bypassed: it was matched against the request (or message) at entry, but the bytes signed were read again after several awaits, so a request edited meanwhile (a reactive form) was signed for a recipient nobody confirmed, including one `checkRecipient` refuses; `PreparedWithdrawal.recipient` and `signed.args` could also disagree with the signed message.
  - Two messages could be signed at one LMS leaf in one process (a fresh memory ledger per attempt, or a ledger that does not keep the contract).
  - A second vault withdrawal could be signed in one process with a key whose signature the process had only read back from a ledger or found on chain.
  - Signed vault-key records of SDK 0.2.0 were silently left out of the multi-device sync: the importing device was told nothing.
  - The window helpers silently accepted a millisecond or `number` "now" (an integrator's `inLaunchWindow(BigInt(Date.now()), …)` always answered false).
  - `verifyLaunch` and `getLaunchFlowStatus` blamed the caller ("nowSecs looks like milliseconds") for an RPC's implausible clock.
  - The header comment of `src/index.ts` (and `dist/index.js`, `dist/index.d.ts`) shipped double-encoded characters.
